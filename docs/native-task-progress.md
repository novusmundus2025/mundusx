# Native coding task progress

The worker reconstructs a compact progress record from the current tagged user request and matched assistant tool calls/host results. It does not add a database, execute tools itself, or share observations between users. The client's conversation remains the source of context.

The record identifies observed source ranges by call ID and content digest, confirmed source writes, and the most recent completed validation command and status. A digest identifies observed bytes; it is not a filesystem version or a claim that external edits cannot occur. Unknown operations and terminal execution invalidate source-read observations. Source changes and environment operations invalidate previous validation results. Failed, truncated, wrapped or incomplete observations do not establish complete coverage.

Before inference, the model receives this compact record and guidance to continue from existing evidence. Before releasing a tool call, the worker permits one covered source refresh, then rejects repeated unchanged reads, growth beyond known EOF, or an identical completed validation without a relevant intervening operation. One bounded correction attempt can choose the next useful action; the rejected call is never executed or streamed to the host. Missing ranges, changed state, incomplete terminal output and new user requests remain inspectable.

For tasks explicitly requiring automated tests or assertions, editor diagnostics, syntax-only validation, printed example results and zero-test runs do not establish completion. The worker requires a successful host exit and a recognized nonempty test-runner report. Unknown reporter formats remain unverified. Functional coverage and application correctness still require appropriate tests; a runner summary alone cannot prove that every requested behavior was tested.

Planning stays in the client's registered planning tool and conversation. Its completion labels are model-reported state, not evidence that builds or tests ran. Compaction that removes tool evidence requires fresh observations rather than inventing retained state.

An explicit first edit of a named, already observed file can be advanced without another planning call. Partial prefix reads expand within the registered read contract. A requested complete replacement keeps related manifest/export/dependency reads available before writing; the first mutation remains bound to its requested target. A separate explicit internal source-artifact substep can compile a complete generated artifact using retained old bytes, but this substep is not inferred automatically from a normal user replacement request. Only the model-facing copy of that obsolete implementation is compacted; original user/system instructions, unrelated source and the actual grounding payload remain intact. Truncated artifacts never become edits, and explanatory prose outside a single fenced artifact does not become source. Markdown and structured data files keep their normal edit path.

Functional assertion failures remain requirements to satisfy. Their stack-frame locations do not automatically force edits to the test; implementation tools stay available. Syntax and compiler diagnostics can still focus a grounded source repair.

When an explicit first edit names a previously observed path, the worker can request fresh source through the registered read tool without asking the model to rediscover the path. Earlier source bytes never ground this new request. A failed host edit also invalidates read observations so an external change can be inspected.

Complete source generation retains every original user, system and developer instruction, with other current source observations quoted as data. Obsolete assistant plans and tool-call examples are omitted only from this internal generation copy to avoid copying the implementation being replaced. The original conversation and host grounding payload are unchanged. Source-generation recovery asks for a shorter complete source artifact rather than a conflicting tool call. These controls do not establish program correctness: actual host execution and suitable tests remain necessary.

The observed-line tool schema stays stable across reads. Changing file paths and line counts live in trailing observation guidance rather than schema enums and descriptions, allowing an incremental model prompt prefix to remain reusable. The compiler still checks the actual observed path, inclusive range, user scope and host contract; a stable schema does not authorize an unread target.

Exact continuation phrases (`continue`, `resume`, and a small set of equivalent task-only phrases) inherit the immediately preceding tagged task. Grounding, original path scope, constraints and verification requirements use that same boundary. New questions, greetings and compound requests establish a new boundary. This is conversation-derived state, not a durable checkpoint or hidden cross-chat memory. The gateway uses the same continuation policy.

Only positive compiler/syntax evidence can force a focused line repair. Runtime stack frames and assertion failures can identify symptoms caused elsewhere, including asynchronous test initialization; they retain the general tools needed to inspect and repair the cause. Duplicate-action recovery has its own feedback and does not tell the model to reread already covered source. The source-artifact output format is an internal system-level adapter instruction; it preserves the user's requested behavior and permissions.

Source artifacts require one complete nonempty fenced block. Narrative promises, unfenced answers, incomplete fences and multiple artifacts cannot become a host edit. This framing validates the artifact boundary, not the correctness of its program.

For ordinary model inference, obsolete assistant/tool transcripts before the effective task boundary are omitted from the model-facing copy. Every user/system/developer instruction and all current-task messages remain. Exact continuation keeps its original boundary and therefore its observations; the untouched payload remains authoritative for host validation and logs. This selection performs no summarization inference and introduces no database state.

Managed Qwen3-Coder runtime capability version 8 constrains registered function names after the model chooses a tool-call marker, including automatic tool selection. Plain answers and pre-call prose remain unrestricted, and command/source/argument values are not filled or repaired by the decoder. The observed-line planner uses a distinct private function name in model-facing schemas; only its validated compiled host replacement reaches the client. Other models and unguarded requests retain their decoding behavior.

An observed failed validation enters a model-facing source-repair phase: inspection and edit tools remain available, while execution tools return after a confirmed source write. This prevents the model from selecting the unchanged failing check as its correction. Recognized environment failures and explicit client-selected tool choices keep their execution path. A source change clears the failed-validation observation and restores normal command selection; no dummy edits or weakened expectations are authorized.

Routine edits use a focused file-tool catalog. Symbol/refactoring helpers, editor-selection helpers and VS Code task orchestration are retained when requested or when an observed task is already active. Explicit client-selected tools are preserved. This changes model-facing selection, not host permissions or the client's installed capabilities.

Planning is available initially and after new host observations, writes or execution results. A completed plan update with no intervening real operation is not another useful model action: the next planning call is rejected and the planning tool is withheld from the next model-facing catalog until work advances. Plan completion labels still do not establish program correctness. Prefix reads clamped at EOF record that boundary, preventing repeated requests for nonexistent higher line ranges until an operation invalidates the observation.

Diagnostic path matching recognizes local `file://` URIs across Windows and POSIX, including percent-encoded spaces and UTF-8. A foreign URI authority is not converted into a local path. Only already observed project paths can produce an automatic registered read. Runtime frames may refresh source after a confirmed edit without forcing a line edit at the symptom; positive compiler evidence still controls focused line repairs. Finite validator rechecks use the same path normalization.

A narrow line replacement that repeats a substantial adjacent unchanged block is rejected before it can duplicate declarations in the host file. The adapter does not guess a wider mutation: recovery receives the rejected range and replacement and can select the correct range or omit the repeated context. Short repeated punctuation and full-file replacements retain their normal behavior.

Private line edits lacking a current prefix observation are converted into a registered fresh read of that same target. The replacement is never released, and the normal host schema, scope and progress checks still validate the read. Other schema errors and traversal failures are not converted. Compile-time rejections retain bounded private argument evidence for correction, stripped from public errors.

Import/load errors that name a known importing file without a line number can refresh that file once after the observed failed check. Unknown module paths do not become read targets. A duplicate-inspection correction during an actual failed-validation phase can focus the bounded model attempt on the observed-file planner; no patch bytes, expected test values or source repairs are invented by this selection.

A covered read can refresh once without a fatal correction attempt, accounting for client context loss and possible external user edits. A changed observation resets this allowance through its actual digest. Repeated identical observations remain bounded, and terminal validation is still not replayed without a source or environment change.

The model-facing context retains the last plain assistant answer for follow-ups while omitting obsolete earlier tool transcripts. Recognized tool-free greetings omit old tool bodies while preserving all user/system/developer messages. Ordinary ambiguous clients retain their normal context. Runtime/assertion failures quote the actual failed check and matched source together near the end of the model view, without restricting edits to the stack-frame symptom. The original payload remains authoritative for grounding; no source repair is generated by the context compiler. Current user acceptance criteria are retained explicitly after the first implementation step, and an old todo list or passing subset of tests is not treated as the full specification.
